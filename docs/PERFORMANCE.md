# Производительность и память

Методика, а не результаты нового замера. В аудите 2026-11-16 игра и бенчмарки не запускались. Цели и бюджеты остаются в [ASSET_BUDGETS.md](../ASSET_BUDGETS.md), разрешения проверок — в [TESTING.md](TESTING.md).

## Уже доступно

- `Game.diagnostics()` и `?diagnostics`: frameMs, calls, triangles, geometries/textures, readyMs, startupMs, initialTransferBytes и состояние игры.
- `npm run check:build`: файловые размеры и gzip, общий размер dist, относительные ссылки из index.html. Общий dist не равен критическому начальному трафику; сейчас скрипт применяет предпочтительный лимит 15 МиБ ко всему dist.
- `npm run audit:first-load`: Chrome, viewport 390×844, DPR 2, три запуска на профиль, холодный HTTP-кэш, gzip, условное замедление CPU/сети. Пишет `verification/first-load/`; сначала нужны исправление старых координат/даты и разрешённая сборка (см. TESTING).
- EconomyTelemetry: добровольные локальные времена/маршруты/покупки текущего сегмента. Это данные баланса, не измерение CPU/GPU или полноценного цикла после reload.

## Как читать метрики

`readyMs` отсчитывается от создания Game до его первого завершённого кадра; `startupMs` — значение performance.now() в тот момент, относительно начала навигации документа. Ни одно само по себе не доказывает первый успешный ввод. `initialTransferBytes` суммирует Resource Timing transferSize к первому кадру: navigation исключён, кэш/незавершённые загрузки/ограничения браузера влияют на итог.

`frameMs` усредняет интервалы кадров, не только время CPU-работы; это не GPU time и не p95. calls/triangles относятся к последнему отрисованному кадру, включая отдельный вид рук/инструмента. `renderer.info.memory` считает объекты геометрий и текстур, не байты видеопамяти и не общую RAM. JS heap, GPU-ресурсы и память процесса браузера измеряются отдельно; если API/инструмент недоступен, писать «не измерено».

## Повторяемый протокол после разрешения

1. Записать commit и dirty-state, ОС/модель устройства, browser/runtime, build mode, viewport/DPR, сеть/CPU throttling, cache policy, seed/фикстуру, звуковые настройки и reduced motion.
2. Для старта использовать свежий контекст, cold cache и одинаковый маршрут: первый кадр, первое движение, первый успешный сбор; без warm-up. Для steady-state прогреть 30 секунд, затем измерять 120 секунд по одинаковому сценарию. Это предлагаемые условия будущего baseline, не описание исторических прогонов.
3. Разделить полный/частичный/пустой стог; стационарный и активный сбор, пылесос, трёх свинок, открытие/закрытие книги, смену инструмента. Для lifecycle выполнить 10 перезапусков и сравнить ресурсы после одинакового idle-периода. Не смешивать сценарии в одну цифру.
4. Сохранить сырые frame samples, median/p95, long tasks, draw calls/triangles, ресурсы renderer, JS heap при поддержке и startup/network timings. Для GPU/process memory указать отдельный инструмент и ограничения. Собирать несколько повторов, сравнивать на том же устройстве; допуски определить по наблюдаемому разбросу.
5. Отдельно проверить реальный мобильный браузер и iframe хостинга. SwiftShader/headless/эмуляция CPU не доказывают mobile FPS, аппаратную GPU-память или результат на itch.io.

## Эталоны и новые результаты

Существующие `verification/*report.json` — исторические наблюдения, не согласованный baseline текущей версии. Будущие согласованные эталоны хранить в `benchmarks/baselines/<scenario>.json`, новые измерения — в `benchmarks/results/<date>-<commit>/`. Создавать эти файлы только с фактическими данными; сейчас их нет.

В отчёте нужны метаданные протокола, сырые samples или ссылка на них, агрегаты, ограничения и команда воспроизведения. Baseline обновлять отдельным видимым изменением с причиной. Сценарий, сборка и параметры должны совпадать; не подменять старый результат новым для сокрытия регрессии. Не оптимизировать визуал и архитектуру по предполагаемым FPS без замеров.
